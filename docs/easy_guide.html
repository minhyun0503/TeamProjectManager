처음에는 시작·기본 용어와 전체 흐름을 읽고 본인 담당으로 이동하세요. 어려운 단어보다 입력값과 처리 결과를 먼저 설명합니다.

먼저 이것만 알고 시작하기

이 프로그램은 팀원들이 할 일, 일정, 메모, 자료와 의견을 함께 관리하는 프로그램입니다. 사용자는 버튼을 누르고, 자바 코드는 그 요청을 처리하고, DB는 결과를 기억합니다.

설명서를 읽을 때 처음부터 모든 파일을 외울 필요는 없습니다. 아래 공통 설명을 읽고, 본인 담당 설명에서 버튼 하나를 골라 끝까지 따라가면 됩니다. 그다음 기존의 자세한 설명서로 범위를 넓히세요.

실행부터 해 보기

  1. Eclipse에서 src/teamproject/common/Main.java를 실행합니다.
  2. 로컬 데모를 선택합니다.
  3. 아이디 demo1, 비밀번호 demo1234를 입력합니다.
  4. 팀 7을 선택합니다.
  5. 업무 관리에서 업무 한 건을 등록해 봅니다.

demo2~demo5도 비밀번호는 같습니다. 화면에 아이디(학번)라고 표시돼 있어도 지금은 demo1을 넣습니다. 실제 조원 학번이 아니라 데모 계정을 등록해 둔 상태입니다.

로컬 데모는 같은 컴퓨터의 파일에 저장합니다. 다른 PC의 로컬 데모와 자동으로 연결되는 것은 아닙니다. 여러 PC에서 공유하려면 같은 MySQL 서버에 연결해야 합니다.

파일 이름을 보면 역할이 보인다

  • Frame / Panel: 사용자가 보는 화면과 버튼 동작입니다.
  • DAO: DB에 어떤 SQL을 보낼지 정합니다. 이름은 Data Access Object의 줄임말입니다.
  • Note / Card / Schedule 같은 작은 데이터 클래스: 메모 한 건, 업무 한 건의 값을 묶어 들고 다닙니다.
  • Renderer: JList의 한 항목을 카드처럼 그립니다. 저장 기능은 없습니다.

예를 들어 NotePanel이 사용자에게 글을 입력받고, NoteDAO가 DB에 저장하고, Note 객체가 조회한 글 한 건을 담습니다. 같은 '메모 기능'이지만 맡은 일이 다릅니다.

번호는 종류를 구분해야 한다

코드의 값 실제 뜻
userId=10 회원 번호가 10인 사람
teamId=7 프로젝트 번호가 7인 팀
taskId=3 업무 번호가 3인 업무
version=2 메모가 두 번째 저장 상태라는 뜻
setInt(1, teamId)의 1 SQL에서 값을 채울 첫 번째 빈자리

회원 번호와 학번도 다릅니다. userid는 DB 내부 번호, studentno는 학번 정보, loginid는 로그인에 쓰는 문자열입니다. 데모에서는 loginid가 demo1입니다.

화면과 DB는 같은 것이 아니다

화면 표는 DB 내용을 읽어 보여 주는 별도 목록입니다. DB에서 저장했다고 표가 저절로 바뀌지는 않습니다. 그래서 저장 후 reload()를 호출해 최신 내용을 다시 읽습니다.

또한 JList/JTable은 보이는 화면 부품이고, DefaultListModel/DefaultTableModel은 그 부품에 보여 줄 데이터 목록입니다. 메뉴판과 메뉴 내용처럼 구분해서 생각하면 됩니다.

브리핑할 때 사용할 문장 틀

“이 버튼을 누르면 A 메서드가 실행됩니다. 여기서 입력값을 읽고 조건을 검사합니다. 정상이라면 B DAO 메서드로 전달하고, DAO가 어떤 표를 어떻게 바꾸는 SQL을 실행합니다. 성공하면 화면을 다시 읽고, 실패하면 어떤 안내를 보여 줍니다.”

어려운 단어를 많이 쓰는 것보다, 이 순서를 코드에서 실제로 가리키며 설명하는 것이 중요합니다.

demo1로 로그인하면 회원 번호 10을 얻습니다. 회원10은 팀7과 팀42에 소속돼 있으므로 팀을 고릅니다. 팀7을 고르면 각 화면이 같은 teamId=7을 사용합니다.

예제: 업무 등록 버튼 한 번 따라가기

사용자가 업무명에 “자료 조사”, 담당자에 데모팀원3, 마감일에 올바른 날짜를 입력했다고 생각해 봅시다.

  1. TaskFrame의 버튼 이벤트가 registerTask를 부릅니다.
  2. showTaskInputDialog가 업무명·담당자·마감일·상태를 받습니다.
  3. 필수 항목과 날짜를 검사합니다. 잘못 입력했다면 DB에 보내기 전에 안내합니다.
  4. TaskDAO.insertTask에 선택한 팀 번호와 입력값을 보냅니다.
  5. DAO는 담당자가 이 팀에 있는지 확인하고 tasks에 새 행을 넣습니다.
  6. 저장이 성공하면 TaskFrame.reload가 업무 표와 진행률을 다시 읽습니다.

다른 기능도 큰 순서는 같습니다. 버튼 이름과 DAO가 사용하는 표가 달라질 뿐입니다.

SQL의 물음표를 실제 값과 연결하기

아래는 SQL 원리를 설명하기 위해 줄인 예제입니다. 완성된 TaskDAO를 대체하는 코드는 아닙니다.

String sql = "SELECT title FROM tasks WHERE team_id = ?";
PreparedStatement p = conn.prepareStatement(sql);
p.setInt(1, teamId);
ResultSet rs = p.executeQuery();
코드 말로 풀기
String sql = ... 실행할 조회 문장을 문자열로 보관
conn.prepareStatement(sql) 이 연결에서 실행할 SQL 준비
p.setInt(1, teamId) 첫 번째 ?에 현재 팀 번호를 정수로 채움
executeQuery() 조회를 실행하고 결과를 받음

teamId가7이면 “tasks에서 팀7의 업무 제목을 찾아 달라”는 요청입니다. setInt(1, teamId)를 보고 “팀1로 고정했다”고 설명하면 안 됩니다.

PreparedStatement는 사용자가 쓴 문자열을 SQL 명령 자체와 구분해 전달하는 데도 도움이 됩니다. 그래서 입력값을 SQL 문자열 뒤에 직접 이어 붙이지 않습니다.

조회 결과를 읽는 while문

while (rs.next()) {
    String title = rs.getString("title");
}

next()는 다음 행이 있는지 확인하면서 그 행으로 이동합니다. 결과가3행이면 본문을3번 실행하고, 없으면0번 실행합니다. 실제 DAO는 읽은 값을 객체나 화면 목록에 넣습니다.

SELECT는 executeQuery()로 결과 목록을 받습니다. INSERT·UPDATE·DELETE는 executeUpdate()로 처리한 행 수를 받습니다. 메서드 이름이 비슷하므로 구분해서 설명하세요.

저장 여러 개를 묶어야 하는 경우

메모 한 번을 저장할 때 메모 본문, 내용 이력, 활동 기록이 함께 저장됩니다. 이 중 본문만 저장되고 이력이 빠지는 상태는 피하고 싶습니다.

코드 뜻
setAutoCommit(false) SQL마다 바로 확정하지 않고 묶어서 처리 시작
commit() 지금까지의 저장을 함께 확정
rollback() 중간에 실패했으므로 이번 묶음을 취소
finally의 setAutoCommit(true) 다음 화면 작업을 위해 기본 상태로 복원

이 묶음을 트랜잭션이라고 합니다. 메모를 업무로 만드는 두 INSERT도 같은 이유로 묶습니다.

모듈은 JDK 기능 묶음, 패키지는 우리가 파일을 나눈 공간, JAR는 외부 라이브러리 파일입니다. 서로 같은 말은 아닙니다.

자동 갱신을 정확하게 설명하기

공유 메모는3초, 아이디어 목록은5초 간격으로 DB를 다시 읽습니다. 이 방식을 폴링이라고 합니다. 저장 즉시 모든 글자가 동시에 바뀌는 공동 편집 방식은 아닙니다.

Timer가 “다시 읽을 시간”을 알리고, SwingWorker의 doInBackground가 별도 연결에서 읽습니다. 읽기가 끝나면 done이 화면 목록을 바꿉니다. Swing 화면을 바꾸는 담당 스레드를 EDT라고 합니다. 별도 연결을 쓰는 이유는 화면의 저장 작업과 배경 읽기가 같은 Connection의 상태를 섞어 쓰지 않게 하기 위해서입니다.

장*민 담당: 프로그램이 시작되고 DB와 연결되는 부분

내 역할을 한 문장으로

프로그램이 사용할 DB를 준비하고, 로그인한 사람의 소속 팀과 공통 저장 기능을 제공합니다.

담당 파일은 common의 Main, DB_connection, SchemaSetup, TeamDAO, ActivityDAO와 schema.sql입니다.

가장 먼저 설명할 예제

demo1로 로그인한 사람이 팀42를 선택했다고 합시다. 회원 번호는10이고, 팀 번호는42입니다. 이후 업무 화면도, 메모 화면도 같은42를 받아야 합니다. 그래야 팀7의 업무가 섞이지 않습니다.

TeamDAO.findTeams는 team_members에서 회원10의 소속을 찾고, teams와 연결해 팀 이름까지 가져옵니다. 서로 다른 표를 공통 번호로 연결하는 것이 JOIN입니다.

파일을 읽는 순서

파일 이 파일에서 찾을 것
DB_connection configure가 접속 정보를 기억하고 open이 실제 Connection을 만드는 부분
TeamDAO findTeams의 회원 조건, requireMember의 소속 검사
Main 실행 방식 선택, DB 준비 후 LoginFrame 생성
SchemaSetup 테이블 준비, users가 비어 있을 때만 데모 계정 생성
ActivityDAO 동작 기록 INSERT와 최근30건 SELECT

DB_connection의 configure는 전화번호를 메모하는 것, open은 실제로 연결을 거는 것에 가깝습니다. 접속 정보를 저장했다고 이미 DB에 연결된 것은 아닙니다.

꼭 구분할 두 가지 비밀번호

  • DB 비밀번호는 DB 서버에 연결할 때 씁니다.
  • 프로그램 비밀번호는 users에서 로그인 계정을 확인할 때 씁니다.

로컬 데모를 선택했다면 DB 접속값은 코드가 준비합니다. 사용자 로그인창에는 demo1 / demo1234를 넣습니다.

requireMember를 쓰는 이유

새 메모를 저장하려면 “회원10이 팀42 소속인가?”를 먼저 확인합니다. 없으면 예외를 전달해 저장을 멈춥니다. 여러 담당자가 같은 검사를 반복해서 다르게 만들지 않도록 공통 메서드로 뺐습니다.

초기 데이터를 매번 넣지 않는 이유

프로그램을 다시 켤 때마다 같은 계정을 넣으면 중복되거나 기존 데이터와 충돌합니다. SchemaSetup은 users에 이미 데이터가 있으면 데모 계정을 다시 넣지 않습니다. 이미 사용 중인 데모 데이터가 자동으로 초기화되는 것도 막습니다.

활동 기록은 누가 확정할까?

ActivityDAO.record는 기록 한 행을 넣습니다. 하지만 그 안에서 commit하지 않습니다. 메모 저장을 호출한 NoteDAO가 본문·이력·활동 기록을 모두 마친 뒤 함께 확정해야 하기 때문입니다.

브리핑 예시

“저는 프로그램 시작과 DB 연결을 담당했습니다. 로그인한 회원 번호로 소속 팀을 조회하고, 선택한 팀 번호를 각 화면에 전달합니다. 새 기능의 저장에서는 공통 소속 검사를 사용합니다. 데모 DB에는 처음 한 번만 가상 계정을 넣고, 이후 사용자가 저장한 내용은 유지합니다.”

이해했는지 확인하기

  • configure와 open의 차이를 설명해 보세요. 설정 보관과 실제 연결의 차이입니다.
  • 회원10이 팀7·42에 속하면 어떤 값을 화면에 넘기나요? 사용자가 선택한 팀 번호입니다.
  • 활동 기록에서 먼저 commit하면 왜 문제인가요? 함께 취소해야 하는 저장이 일부 먼저 확정될 수 있기 때문입니다.

내 역할을 한 문장으로

사용자가 누구인지 확인하고, 팀원 정보를 관리하며, 팀이 함께 쓰는 메모를 저장하고 보여 줍니다.

담당 파일은 member의 UserDAO, LoginFrame, MemberDAO, MemberFrame, NoteDAO, NotePanel입니다.

로그인 버튼을 누르면

LoginFrame.doLogin이 빈 입력인지 확인합니다. UserDAO.login은 아이디·비밀번호로 users를 조회합니다. 맞으면 회원 번호와 이름을 담은 User를 반환하고, 틀리면 null을 반환합니다. 로그인 성공 뒤에는 TeamDAO로 소속 팀을 조회하고 MainFrame을 엽니다.

이름만 반환하지 않는 이유는 동명이인이 있을 수 있고, 팀 조회·작성자 저장에는 정확한 회원 번호가 필요하기 때문입니다.

팀원 등록은 왜 INSERT가 두 번일까?

users에는 “누구인가”를 저장하고, team_members에는 “어느 팀 소속인가”를 저장합니다. 새 계정을 만든 뒤 그 회원 번호로 소속을 등록합니다. 하나라도 실패하면 두 작업을 모두 취소합니다. 팀원 삭제는 소속만 지우며 계정 자체는 남깁니다.

메모는 한 건을 어떻게 들고 다닐까?

Note 객체는 메모 번호, 제목, 내용, 작성자 번호, 수정자 이름, 수정 시각, 버전 번호를 묶습니다. 여러 메모를 읽으면 List가 됩니다. NotePanel은 이 목록을 JList에 보여 주고, 선택한 글의 내용을 오른쪽에 표시합니다.

새 메모 저장을 따라가기

  1. 새 메모 버튼 → NotePanel.edit(null).
  2. 제목·내용 입력 → NoteDAO.save 호출.
  3. id가0이므로 새로운 notes 행 INSERT.
  4. getGeneratedKeys로 방금 만든 note_id 받기.
  5. notehistory에 첫 내용 저장, activitylog에 저장 기록 추가.
  6. commit 후 화면 목록 reload.

메모 번호를 가장 큰 숫자로 추측하지 않고 생성 결과에서 받습니다. 다른 사용자가 동시에 등록해도 내가 만든 메모의 번호를 알아야 하기 때문입니다.

두 사람이 같은 메모를 고치면?

A와 B가 모두 버전1을 열었습니다. A가 먼저 저장하면 DB는 버전2가 됩니다. B가 저장할 때 “아직 버전1인가?” 조건을 확인합니다. 이미2이므로 일치하는 행이 없고 수정 결과가0입니다.

if (p.executeUpdate() == 0) {
    conn.rollback();
    return false;
}

이 부분은 “수정할 수 있는 행이 없으니 이번 저장을 취소하고 실패를 알려라”는 뜻입니다. B의 오래된 입력으로 A의 최신 내용을 덮어쓰지 않습니다. 화면은 B의 입력을 편집창에 남겨 두고 안내합니다.

이처럼 저장 순간에 버전을 비교하는 방법을 낙관적 잠금이라고 부릅니다. 어려운 이름보다 “버전1을 읽었으면 버전1인 동안만 수정한다”는 규칙을 먼저 이해하세요. 자동으로 두 글을 합치지는 않습니다.

자동 새로고침과 편집창을 나눈 이유

목록은3초마다 다시 읽습니다. 하지만 별도 편집창의 입력은 자동으로 바꾸지 않습니다. 다른 사람이 글을 썼다고 내가 입력 중인 문장을 잃으면 안 되기 때문입니다. 목록 조회 중에는 loading 표시로 같은 조회를 겹쳐 시작하지 않습니다.

브리핑 예시

“로그인은 회원 번호와 이름을 반환합니다. 공유 메모는 목록과 편집창을 분리했고, 저장할 때 읽었던 버전 번호를 검사합니다. 먼저 저장한 사람이 버전을 올리면, 나중 사람은 수정 행 수가0이 되어 충돌을 안내받습니다. 목록 자동 갱신과 수정 충돌 검사는 서로 다른 기능입니다.”

이해했는지 확인하기

  • 자동 갱신만 있으면 수정 충돌도 막히나요? 아닙니다. 별도로 version 조건이 필요합니다.
  • 메모 저장 뒤 이력 저장에 실패하면? 이번 메모 변경도 rollback합니다.
  • 팀원 삭제는 로그인 계정도 삭제하나요? 아니요. 팀 소속만 삭제합니다.

윤*훈 담당: 업무 관리·보드·메모에서 업무 만들기

내 역할을 한 문장으로

업무를 등록·수정·삭제하고, 같은 업무를 상태별 카드나 내 업무 목록으로 보여 줍니다.

담당 파일은 task의 TaskDAO, TaskFrame, TaskBoardPanel, TaskCardRenderer, TaskFromNoteDialog입니다.

업무 표와 보드는 서로 다른 DB일까?

아닙니다. 둘 다 tasks를 읽습니다. 업무 표는 행으로, 보드는 카드로 보여 줄 뿐입니다. 보드에서 완료로 바꾸고 업무 표를 다시 열면 같은 업무가 완료로 보입니다.

보드에 카드를 나누는 과정

업무가 다음과 같다고 생각해 봅시다.

업무 상태 들어갈 칸
자료 조사 할 일 첫 번째 목록
화면 제작 진행 중 두 번째 목록
DB 연결 완료 세 번째 목록

TaskBoardPanel.reload는 먼저 세 목록을 비웁니다. TaskDAO.board가 반환한 업무를 하나씩 읽고, STATUS_LIST의 상태 이름과 비교해 맞는 목록에 넣습니다. 상태3개가 고정되어 있으므로 업무가 늘면 그 수에 비례해 처리량도 늘어납니다. 이것을 대략 O(n)이라고 설명할 수 있습니다.

내 업무만 보기

로그인한 회원 번호가30이면 assignee_id가30인 업무만 고릅니다. 이름으로 비교하지 않습니다. 팀 조건도 함께 있어야 다른 팀에서 맡은 업무가 섞이지 않습니다.

보드의 상태 변경 버튼은 선택한 task_id로 UPDATE합니다. 카드가 다른 칸에 새로 복사 저장되는 것이 아닙니다. 상태가 바뀐 뒤 목록을 다시 읽어 다른 칸에 보이게 됩니다.

TaskCardRenderer는 무엇일까?

Card 객체에는 제목·담당자·마감일 같은 값이 있습니다. Renderer는 그 값을 JLabel에 넣어 카드 모양으로 보여 줍니다. 데이터를 저장하는 클래스가 아닙니다. JList가 항목을 그릴 때 자주 호출하므로 여기서 SQL을 실행하지 않습니다.

메모를 업무로 만드는 과정

회의 메모가 “자료 조사 담당자를 정하자”라면, 업무로 등록 버튼에서 담당자와 마감일을 정합니다.

  1. TaskFromNoteDialog가 제목·담당자·날짜를 받습니다.
  2. TaskDAO.insertFromNote가 같은 팀의 메모와 담당자인지 확인합니다.
  3. tasks에 업무를 넣고 새 task_id를 받습니다.
  4. tasknotes에 taskid와 note_id를 함께 저장합니다.
  5. 두 INSERT가 모두 성공하면 commit합니다.

task_notes는 “업무3은 메모5에서 나왔다”는 연결 정보입니다. 업무만 생기고 연결이 빠지는 상태를 막으려고 두 저장을 묶습니다.

메모를 삭제해도 이미 만든 업무는 남습니다. 생성 당시 내용은 업무 설명에 복사되어 있습니다. 원본 메모 보기 버튼은 연결된 메모의 현재 내용을 조회합니다.

기존 업무 관리에서 놓치면 안 되는 부분

TaskFrame은 선택한 표 행의 첫 열에서 실제 task_id를 읽습니다. 표의 세 번째 행이 반드시 업무3은 아닙니다. 삭제 후 번호가 빠지거나 정렬이 달라질 수 있기 때문입니다.

등록·수정·삭제 후 reload는 표와 진행률을 함께 갱신합니다. fitColumns는 각 열에서 가장 긴 내용의 너비를 찾아 표가 잘리지 않게 합니다. 열마다 모든 행을 확인하므로 행n개·열c개에 대략 O(n×c) 비교입니다.

브리핑 예시

“표와 보드는 같은 tasks 데이터를 사용합니다. 보드는 상태 문자열에 따라 세 목록으로 나누고, 내 업무 필터는 로그인 회원 번호로 조회합니다. 메모에서 업무를 만들 때는 업무 번호를 생성 결과에서 받아 연결 표에 넣고 두 작업을 함께 확정합니다.”

이해했는지 확인하기

  • 카드를 완료로 바꾸면 업무 행이 하나 더 생기나요? 아니요. 기존 행의 상태가 바뀝니다.
  • 업무 생성 후 연결 저장에 실패하면? 업무 생성도 함께 취소합니다.
  • 표의 행 번호를 task_id로 쓰면? 다른 업무를 수정·삭제할 수 있습니다.

이*주 담당: 진행률·마감 안내·일정 달력

내 역할을 한 문장으로

업무가 얼마나 끝났는지 계산하고, 남은 날짜와 팀의 일정을 보여 줍니다.

담당 파일은 schedule의 InlineProgressData, InlineProgressDAO, InlineProgressPanel, ScheduleDAO, SchedulePanel입니다.

진행률은 이렇게 계산한다

전체 업무가4개이고 완료가1개면 25%입니다.

완료 업무 수 ÷ 전체 업무 수 × 100

getTotalCount는 전체 개수, getCompletedCount는 완료 개수, getPercent는 퍼센트를 계산합니다. 회원 번호0은 이 계산에서 '전체'를 뜻하도록 정한 값입니다. 실제 로그인 회원을0으로 고정한 것이 아닙니다.

전체가0개면 나누기 전에0%를 반환합니다. 계산에100.0을 사용해 소수점이 바로 버려지는 것을 피하고 Math.round로 반올림합니다. 따라서 완료2개/전체3개는67%입니다.

마감 안내는 조건의 순서가 중요하다

먼저 확인할 것 표시
이미 완료한 업무인가? 완료
마감일이 없는가? 마감일 없음
마감일이 오늘보다 과거인가? 지연 N일
마감일이 오늘인가? 오늘 마감
그 외 미래 날짜인가? D-N

완료 확인을 먼저 하므로 마감일이 지났어도 완료 업무를 지연으로 표시하지 않습니다. 날짜 차이는 ChronoUnit으로 계산합니다.

DAO는 DB에서 데이터를 읽고, Data는 개수·날짜를 계산하고, Panel은 막대와 글자를 보여 줍니다. 계산과 화면을 나누면 어느 쪽이 틀렸는지도 찾기 쉽습니다.

여러 달에 걸친 일정은 어떻게 찾을까?

10월30일~11월2일 일정은11월 달력에도 보여야 합니다. 시작일이11월인지만 보면 이 일정이 빠집니다.

그래서 두 조건을 동시에 확인합니다.

  • 일정 시작일이 이번 달 마지막 날보다 늦지 않다.
  • 일정 종료일이 이번 달 첫날보다 이르지 않다.

즉, 두 기간이 하루라도 겹치면 가져옵니다. ScheduleDAO.list의 날짜 조건이 이 역할입니다.

달력의 빈칸은 어떻게 정할까?

1일이 목요일이라면 월·화·수 세 칸을 비운 뒤1일을 넣습니다. getDayOfWeek().getValue()는 월요일1~일요일7이므로1을 빼면 앞쪽 빈칸 개수가 됩니다.

그다음1일부터 그달 마지막 날까지 반복합니다. 각 날짜가 일정 시작일~종료일 사이면 그 칸에 일정명을 넣습니다. YearMonth가 월 길이를 알려 주므로2월을 직접28일로 고정하지 않습니다.

저장할 때 무엇을 검사할까?

SchedulePanel은 입력 문자열을 LocalDate로 바꿉니다. 날짜 형식이 잘못됐으면 안내합니다. ScheduleDAO.save는 종료일이 시작일보다 앞서지 않는지 검사합니다. 정상일 때만 일정과 활동 기록을 함께 저장합니다.

달력에서 수정할 칸을 바로 누르는 기능은 없습니다. 일정 목록 탭에서 행을 선택한 뒤 수정·삭제합니다.

브리핑 예시

“진행률은 tasks의 전체·완료 개수로 계산하고, 일정은 별도의 schedules에서 읽습니다. 달력은 표시할 달과 기간이 겹치는 일정을 가져온 뒤 날짜 칸마다 배치합니다. 첫날 요일과 월 길이는 자바 날짜 API로 구합니다.”

이해했는지 확인하기

  • 업무가0개면 진행률은? 0%입니다.
  • 완료한 업무의 마감일이 어제면? 지연이 아니라 완료입니다.
  • 10/30~11/2 일정은11월에 보이나요? 보입니다. 두 기간이 겹칩니다.

신*준 담당: 통합 화면·자료·아이디어·댓글·공감

내 역할을 한 문장으로

여러 기능을 탭으로 연결하고, 자료와 아이디어를 올려 서로 의견을 나눌 수 있게 합니다.

담당 파일은 resource의 MainFrame, DashboardPanel, MaterialDAO, MaterialPanel, IdeaDAO, IdeaPanel, IdeaCardRenderer, ActivityPanel입니다.

통합 화면은 무엇을 넘겨 줄까?

MainFrame은 로그인한 User와 선택한 Team을 받습니다. 각 화면에 같은 팀 번호를 보내고, 작성자가 필요한 화면에는 회원 번호도 보냅니다. 탭을 바꾸면 그 화면의 reload를 불러 다른 탭에서 바뀐 내용을 확인합니다.

자료 관리는 링크를 저장한다

자료명·설명·주소를 입력하면 materials에 저장합니다. uploader_id에는 로그인한 사람의 번호를 넣습니다. 링크 열기 버튼은 Desktop을 통해 기본 브라우저에 주소를 전달합니다. 파일 자체를 서버로 업로드하는 기능은 아닙니다.

DashboardPanel은 진행률, 오늘 마감·지연 업무, 업무 목록과 최근 자료를 모아 보여 줍니다. 계산값은 진행률 담당 코드를 사용하므로 같은 계산을 화면마다 다시 만들지 않습니다.

게시물·댓글·공감은 왜 따로 저장할까?

테이블 한 행이 뜻하는 것
ideas 아이디어 글 한 개
idea_comments 어떤 글에 누가 쓴 댓글 한 개
idea_reactions 어떤 글에 어떤 사용자가 공감했다는 표시 한 개

이렇게 나누면 한 글에 댓글 여러 개가 달려도 관리할 수 있습니다. 공감도 숫자만 저장하지 않고 누가 눌렀는지 기억할 수 있습니다.

공감 버튼을 두 번 눌러 보기

첫 클릭 전에 내 공감이 없다고 가정합니다.

  1. 내 공감 행을 DELETE해 봅니다.
  2. 삭제한 행이0개면 원래 없었다는 뜻입니다.
  3. 그러면 INSERT해서 공감을 만듭니다.
  4. 다시 누르면 이번에는 DELETE 결과가1입니다.
  5. 이번에는 INSERT하지 않아 공감이 취소됩니다.

DB의 (ideaid, userid) 조합을 기본키로 정해 한 사람이 같은 글에 공감 행을 여러 개 만들 수 없게 했습니다. 이것을 복합 기본키라고 합니다.

댓글과 작성자 권한

IdeaPanel이 댓글 문자열을 읽고 IdeaDAO.comment가 빈 값·길이·팀을 검사한 뒤 저장합니다. 성공한 뒤에만 댓글 입력칸을 비웁니다.

아이디어 수정·삭제는 글 번호뿐 아니라 팀 번호와 작성자 번호도 확인합니다. 화면에서 버튼을 눌렀다는 사실만 믿지 않고 DAO의 SQL에서도 조건을 둡니다.

카드와 최근 활동

IdeaCardRenderer는 제목·작성자·댓글 수·공감 수를 카드처럼 그립니다. SQL은 실행하지 않습니다. IdeaPanel의 목록은5초마다 다시 읽습니다.

ActivityPanel은 ActivityDAO가 반환한 최근 활동 문자열을 목록에 넣습니다. 현재는 메모·일정·아이디어 저장, 댓글·공감이 기록 대상입니다. 모든 기존 기능의 모든 동작을 기록하는 것은 아닙니다.

브리핑 예시

“저는 선택한 팀의 통합 화면과 자료·아이디어 화면을 담당했습니다. 게시물·댓글·공감은 별도 표로 나누었고, 공감은 글 번호와 회원 번호를 함께 기본키로 사용합니다. 카드 렌더러는 표시만 맡고, DAO가 실제 저장을 처리합니다.”

이해했는지 확인하기

  • 공감 수만 저장하면 어떤 정보가 없을까요? 누가 눌렀는지 몰라 중복·취소 처리가 어렵습니다.
  • Renderer에서 저장도 하나요? 아니요. 화면 모양만 만듭니다.
  • 다른 사람의 글을 수정할 수 있나요? 아이디어 수정·삭제는 작성자 조건으로 제한합니다.
