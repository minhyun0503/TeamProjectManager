# 이*찬 담당: 로그인·팀원 관리·공유 메모

## 내 역할을 한 문장으로

**사용자가 누구인지 확인하고, 팀원 정보를 관리하며, 팀이 함께 쓰는 메모를 저장하고 보여 줍니다.**

담당 파일은 member의 UserDAO, LoginFrame, MemberDAO, MemberFrame, NoteDAO, NotePanel입니다.

## 로그인 버튼을 누르면

LoginFrame.doLogin이 빈 입력인지 확인합니다. UserDAO.login은 아이디·비밀번호로 users를 조회합니다. 맞으면 회원 번호와 이름을 담은 User를 반환하고, 틀리면 null을 반환합니다. 로그인 성공 뒤에는 TeamDAO로 소속 팀을 조회하고 MainFrame을 엽니다.

이름만 반환하지 않는 이유는 동명이인이 있을 수 있고, 팀 조회·작성자 저장에는 정확한 회원 번호가 필요하기 때문입니다.

## 팀원 등록은 왜 INSERT가 두 번일까?

users에는 “누구인가”를 저장하고, team_members에는 “어느 팀 소속인가”를 저장합니다. 새 계정을 만든 뒤 그 회원 번호로 소속을 등록합니다. 하나라도 실패하면 두 작업을 모두 취소합니다. 팀원 삭제는 소속만 지우며 계정 자체는 남깁니다.

## 메모는 한 건을 어떻게 들고 다닐까?

Note 객체는 메모 번호, 제목, 내용, 작성자 번호, 수정자 이름, 수정 시각, 버전 번호를 묶습니다. 여러 메모를 읽으면 List<Note>가 됩니다. NotePanel은 이 목록을 JList에 보여 주고, 선택한 글의 내용을 오른쪽에 표시합니다.

## 새 메모 저장을 따라가기

1. 새 메모 버튼 → NotePanel.edit(null).
2. 제목·내용 입력 → NoteDAO.save 호출.
3. id가0이므로 새로운 notes 행 INSERT.
4. getGeneratedKeys로 방금 만든 note_id 받기.
5. note_history에 첫 내용 저장, activity_log에 저장 기록 추가.
6. commit 후 화면 목록 reload.

메모 번호를 가장 큰 숫자로 추측하지 않고 생성 결과에서 받습니다. 다른 사용자가 동시에 등록해도 내가 만든 메모의 번호를 알아야 하기 때문입니다.

## 두 사람이 같은 메모를 고치면?

A와 B가 모두 버전1을 열었습니다. A가 먼저 저장하면 DB는 버전2가 됩니다. B가 저장할 때 “아직 버전1인가?” 조건을 확인합니다. 이미2이므로 일치하는 행이 없고 수정 결과가0입니다.

```java
if (p.executeUpdate() == 0) {
    conn.rollback();
    return false;
}
```

이 부분은 “수정할 수 있는 행이 없으니 이번 저장을 취소하고 실패를 알려라”는 뜻입니다. B의 오래된 입력으로 A의 최신 내용을 덮어쓰지 않습니다. 화면은 B의 입력을 편집창에 남겨 두고 안내합니다.

이처럼 저장 순간에 버전을 비교하는 방법을 **낙관적 잠금**이라고 부릅니다. 어려운 이름보다 “버전1을 읽었으면 버전1인 동안만 수정한다”는 규칙을 먼저 이해하세요. 자동으로 두 글을 합치지는 않습니다.

## 자동 새로고침과 편집창을 나눈 이유

목록은3초마다 다시 읽습니다. 하지만 별도 편집창의 입력은 자동으로 바꾸지 않습니다. 다른 사람이 글을 썼다고 내가 입력 중인 문장을 잃으면 안 되기 때문입니다. 목록 조회 중에는 loading 표시로 같은 조회를 겹쳐 시작하지 않습니다.

## 브리핑 예시

“로그인은 회원 번호와 이름을 반환합니다. 공유 메모는 목록과 편집창을 분리했고, 저장할 때 읽었던 버전 번호를 검사합니다. 먼저 저장한 사람이 버전을 올리면, 나중 사람은 수정 행 수가0이 되어 충돌을 안내받습니다. 목록 자동 갱신과 수정 충돌 검사는 서로 다른 기능입니다.”

## 이해했는지 확인하기

- 자동 갱신만 있으면 수정 충돌도 막히나요? **아닙니다. 별도로 version 조건이 필요합니다.**
- 메모 저장 뒤 이력 저장에 실패하면? **이번 메모 변경도 rollback합니다.**
- 팀원 삭제는 로그인 계정도 삭제하나요? **아니요. 팀 소속만 삭제합니다.**
